## 變慢從哪一天、哪個 commit 開始

拉 400 次成功部署的時長按日取中位數，斷點非常乾淨：09-06 還是 10.4 分，09-07 上午 10:31 那次起變 35 分，之後一路爬到 10 月的 40 分。斷點落在 PR #1682（Astro 6→7 升級，`a03f19009`）。同頁數（14,151）的 CI log 比對：astro 靜態產生 168 秒 → 1,544 秒，每一類頁面都慢 7 到 15 倍，連 raw markdown 端點也一樣，代表是全站共同的一層。本機 CPU profile 直接指名：同一個 PR 加進來的 `src/middleware.ts` 對每頁輸出的 HTML 呼叫 `renderUiIcons()`，用 parse5 建完整的樹（含原始碼位置）再走一遍，把 emoji 換成 Island Lines SVG，佔 57%，它製造的 GC 再佔 30%。全站 HTML 合計 4.9GB。13 個語言的 /changelog 各 11.7MB，parse5 一頁要 19 到 30 秒。

## 修法：單趟掃描，parse5 會修補的地方整頁退回原實作

`scanUiIcons` 只追蹤標籤巢狀與保護區（head、pre、code、blockquote、svg、`.prose` 等），照 WHATWG 規格重現 parse5 對乾淨文件建出的樹；遇到 parse5 會修補的寫法（誤巢狀、表格寄養、head 提早結束、非 ASCII 字元參照）就整頁交回原本的 parse5 實作，原碼一字不改留作 `renderUiIconsReference`。第一版保守到 94% 的頁面都退回，逐條補上三個真實常見的形狀才降到 3%：Tailwind 任意變體把 `&amp;`、`&gt;` 寫進每個 class；Astro 在 `</body></html>` 之後還放 `<script>`，parse5 會把它收回 body，而且 body 結尾的文字節點位置會橫跨 `</body>`；PageHero 副標有 `<p> <p>` 與 `<p> <div>`。另一個是我自己造的平方級：註解結尾同時找 `-->` 與 `--!>`，後者幾乎不存在，每個註解都掃到文件尾。

驗證工具 `scripts/tools/verify-ui-icons.mjs` 多執行緒逐頁比對兩條路徑，也能拿一次正常 build 的產出對參考實作。結果：19,665 頁兩條路徑全同，同一份輸入的 build 每頁 HTML 與參考實作逐位元組相同，非 HTML 只有 feed.xml 的 lastBuildDate 不同。比對途中兩次假警報都是輸入變了：一次是我在兩次 build 之間還原了 prebuild 重產的資料檔（1145 篇變 1141），一次是 rebase 進新 commit（changelog 與首頁多列三筆）。dashboard 的「N 小時前」是 build 當下算的，每次都會差。

## 另外三刀

`status.py` 的 git log 改成 `--full-history HEAD -- knowledge`（`2905bf1d7`）：17,881 個路徑的歷史逐筆相同，CI 上這步 84 秒 → 32 秒。changelog 的 `git log -n 9999` 在 production build 共用第一次的結果（`e9865f3dc`），原本 13 個語言各同步跑一次、卡住 render 執行緒。最後把圖示掃描搬到 worker 執行緒（`b9525e4fc`）：Astro 只用一條執行緒產生頁面，CI 的 4 顆 vCPU 有三顆閒著。

## Beat 5 — 反芻

變慢的那一天，有三個地方都看得到它：CI 的 Build 一步從 5 分鐘變 26 分鐘，build-perf 儀表板每天畫這條線，pre-push hook 每次 push 都去 GitHub 量一次典型時長。九月底有一班量到 2,348 秒，修的是 hook 的等待邏輯，讓它跟著新的中位數走。三個儀器都誠實記錄，沒有一個問「為什麼」，因為它們拿來比較的基準就是最近幾次自己。今天上午 feedback-triage 那班才寫下「經驗最大值會把它標示過的那次事件吸收進自己」，下午這個換成中位數又出現一次，而且吸收得更快：五次慢的 run 之後，退化就是典型。

另一件值得留下的是驗證方式。要讓一支手寫掃描器在 19,665 頁上跟 parse5 一個位元組都不差，靠的是把原實作原封不動留著，當退路也當尺，再造一支能整站重跑比對的工具。兩次比對失敗都先懷疑輸入有沒有變，查下去果然都是輸入的問題。
